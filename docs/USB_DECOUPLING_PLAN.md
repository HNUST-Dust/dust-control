# 减少 USB 依赖的详细整改计划

> 当前决策：USB 与 EtherCAT 方案分别维护，不要求同一套运行时随时切换后端。
> 因此本计划暂不实施，保留为此前以可替换后端为目标的设计讨论。
> 不为未来切换新增 CAN/UART 抽象接口，也不批量迁移设备所有权。
> 后续优先处理已影响阅读和维护的问题，例如区分控制停顿期限与 USB 会话租约。
> 控制算法和设备协议继续保持独立，USB 运行时及 DustControl 装配可直接依赖具体 USB 实现。

这是实现前的计划。目标是让业务运行时和设备状态不再绑定 USB，同时保留现有通信字节、控制行为、线程与队列结构。

## 1. 用接口替换现有端口转发

**问题**：CanCommandPort、UartFramePort 虽然名字通用，内部却持有 UsbTransmitter 引用。业务包含其头文件时也引入了 USB 实现。

**措施**：

- 将现有两个类型迁至拟新增的 `src/hardware/adapter_interfaces.hpp`；保持 `dust_control::host` 命名空间，它表达主机侧能力，并不专指 USB。
- 两个类型改为小型抽象接口，由现有 UsbTransmitter 直接继承和实现。
- CAN 接口包括 ConfigureCan、SubmitCan、healthy、error；UART 接口包括 SubmitUart。业务接口不提供启停和资源回收操作。
- CanProducer、CanCommandGroup 等接口所需数据定义一并迁移，不能反向包含 USB 头。
- 删除原端口内部的 UsbTransmitter 引用及转发实现；不保留旧包装，也不另建 UsbCommandAdapter。

**代价及边界**：接口调用改为一次虚分派。两个接口对应同一个 UsbTransmitter 对象，不生成额外发送器、工作线程或消息队列。

**验收**：使用测试后端就能满足接口；公共接口头不包含 USB、libusb、ROS 或 YAML 实现。

## 2. 让底盘、云台、UI 使用端口能力

**问题**：ChassisMotorAdapter 持有 UsbTransmitter 指针；云台和 UI 的端口又绑定具体发送器。更换后端必须修改业务类型。

**措施**：

- ChassisMotorAdapter 使用借用的 CanCommandPort 指针。
- GimbalDevices 使用同一种借用端口；UiDevices 使用 UartFramePort 指针，以空指针表达当前已有的离线状态。
- 注册及提交时显式传入 CanProducer。来源身份、命令组冲突检查仍由发送后端执行；不能仅靠去掉旧端口中的 producer 字段而丢掉来源区分。
- 业务只取得需要的端口，不取得完整 UsbSession、UsbLink 或后端启停权限。
- MotorEncoder 和控制器现阶段留在原位置，不借这次调整更换电机编码路径。

**保留行为**：CAN 多来源仲裁、每来源期限、递增序号、生成时间、空批次活性语义、UART FIFO 与过期策略均保留；提交成功仍只表示同步复制/接纳，不表示硬件完成。

**验收**：底盘、云台、UI 的自有源码不再引用 USB 类型、头文件或 USB 协议常量；使用无 USB 的测试发送实现可验证生命周期与数据提交。

## 3. 将设备所有权交还 Adapter 装配对象

**问题**：UsbLink 直接拥有 MotorFeedbackDecoder、WflySbusDecoder、Hi91Decoder、RefereeDecoder 和 OnboardImu，使设备状态的寿命依附于 USB 连接对象。

**措施**：

- 将五个设备对象迁至现有 DustControl::Adapter 内，保留每个 Adapter 各自独立的实例。
- DustControl 使用本板 MotorConfig 子集、IMU 配置和原有 CRC 设置构造设备；不创建全局共享解码器。
- UsbSession / UsbLink 改为借用接收目标；已有 Decoder 访问函数从 UsbLink 中删除，DustControl 直接把设备 Read 接口交给业务。
- 如需要减少构造参数，公共头中可定义只包含具名借用引用/指针的接收目标结构；它不拥有设备，没有转发方法，不形成运行时调用层。
- 不增加 DevicesManager、DeviceProxy 或新的设备分派对象。

**验收**：设备对象数量不变；UsbLink 不再按值保存设备；各板相同 bus/ID 仍只更新归属板的设备。直接离线构造设备不需要 USB 对象。

## 4. 明确 USB 报告处理与设备接收的边界

**问题**：移动所有权后，如果时间换算、断流通知或遥控定时检查被遗漏，会形成表面解耦、实际行为退化。

**措施**：

- usb_receive.cpp 继续检查 USB 报告类型、字段与长度，使用本板绑定把有效 CAN/UART/板载 IMU 数据交给借用设备。
- 设备只消费原始 CAN 载荷、UART 字节、采样时间及序号，不消费 UsbInPacket。
- 保留 MCU 发报时间与采样时间的回绕年龄计算；遥控丢帧计时仍使用原来的主机到达时间。
- UART 序号跳变继续触发 Discontinuity；Ready 仍在接收线程重置本板设备和接收状态。
- USB 事件循环继续轮询所借用 WflySbusDecoder 的 PollTimeout，保证没有新 UART 字节时也会触发既有丢帧超时。
- UartReceiveQueue 本轮留在 USB 会话中：它当前缓存的是 USB UART 报告，不将其泛化成通用串口框架。

**验收**：分片、多帧、丢块、静默遥控超时、时间回绕、CRC 设置和快照读取测试保持原结果；USB 不直接解析设备内部协议字段。

## 5. 将设备接线从 USB 连接选项中分离

**问题**：UartSensorBindings、HI91 CRC 选择和是否解码电机，目前与 VID/PID、serial 等混在 UsbOptions 中。

**措施**：

- UART 设备绑定归本板 Adapter 的装配配置，保留现有通道范围和重复绑定校验。
- strict_hi91_crc 用于构造本板 Hi91Decoder；本板是否有电机由现有 MotorConfig 子集决定。
- UsbOptions 保留真正属于 USB 的设备身份、接收线程等选项；UsbTransmitOptions 保留 USB 发送调度配置。
- 当前 YAML schema、键名、默认值和错误检查维持兼容，这一步调整内存归属，不要求用户重写配置。
- DustControlConfig 作为装配配置仍可显式使用 USB 类型；暂不增加无实现的 transport 枚举、EtherCAT 配置或通用工厂。

**验收**：现有配置全部仍可加载，非法绑定仍在启动前拒绝；设备构造和业务配置无需从 UsbOptions 读取设备策略。

## 6. 拆开含义不同的期限

**问题**：kCommandTimeoutUs 位于 USB 发送器头，底盘为了控制停顿检查和来源期限而依赖它；同一个名字还影响 USB 租约、报告健康和采样年龄限制。

**措施**：

- 底盘可容忍的控制停顿归 ChassisRuntimeOptions，来源提交期限由装配处传给现有注册接口。
- USB 最大请求租约、USB 流健康检查、采样年龄检查各归其具体实现，不能把它们重新命名成一个所有后端共用的 20 ms 常量。
- 本轮保持所有现有数值、单位和比较边界；不增加一组未经需求确认的 YAML 可调参数。
- USB 的实际租约继续取主机上限与 Ready 固件上限中的较小值；来源失效仍停止本板完整会话。

**验收**：底盘不再引用 USB 常量；等于期限时是否过期、旧序号是否续期、目标过期后的行为均与原实现一致。

## 7. 固定线程所有权、启动与回收顺序

**问题**：设备移到父对象后，接收线程借用的引用和业务端口更容易出现寿命错误；多板依次停止还可能消耗其他板租约。

**措施**：

- 接收线程继续独占 Consume、Reset、Discontinuity、PollTimeout；业务只通过 Read 取得快照，移动所有权不改变写线程。
- Adapter 先构造设备，再构造借用设备的 USB 会话；成员声明顺序保证析构时先销毁会话，再销毁设备。
- 业务注册命令组后，维持现有启动时序：底盘先运行，各板就绪后立即产生安全输出，全部启动成功前整机输出许可保持关闭。
- 任一后续板启动失败，回收已启动的板和业务；不重新 Arm、不继续局部输出。
- 退出仍先停止全部业务，再向所有发送器 RequestStop，之后逐个 Stop/Close、等待回调和线程退出，最后释放设备。
- 离线、禁用模块和没有真实 CAN 生产者时的 idle 行为保留。

**验收**：两板、三板、延迟握手、后板 Arm 拒绝、断连和重复 Stop 测试通过；ASan 或同类检查可在发现寿命疑点时补充，不以工具堆叠代替所有权检查。

## 8. 从构建依赖上完成隔离

**问题**：即使源码改用接口，业务库继续链接 dust_usb，仍然会携带 USB 依赖，无法证明业务独立。

**措施**：

- 公共端口为头文件声明，使用已有 dust_headers；不新增只为转接的运行时库。
- dust_chassis_runtime 去掉 dust_usb，显式链接其实际使用的电机、IMU、遥控和实时支持库。
- dust_gimbal、dust_ui 去掉 dust_usb，按其真实符号使用保留设备与实时支持依赖，避免继续依赖 USB 的传递链接。
- DustControl / dust_startup 继续链接 dust_usb，因为它们负责当前具体后端的装配。
- dust_usb 继续依赖设备协议实现，因为当前接收处理直接调用借用设备的高层方法。
- 顶层是否可完全不安装 libusb 是另一项可选后端构建能力；本轮不把业务库隔离夸大成整个工程已经支持无 libusb 构建。

**验收**：不链接 dust_usb 的业务测试目标可以构建运行；链接关系和 include 检查都能识别重新引入的 USB 依赖。

## 9. 用针对性约束防止回退

**问题**：头文件位置和命名调整无法防止以后重新把 UsbTransmitter 传给业务，或者在公共接口塞入 USB 包类型。

**措施及验收**：

| 检查 | 解决的问题 |
|---|---|
| 公共接口独立编译及 include 检查 | 防止公共端口暗含 USB / libusb / ROS 实现 |
| 业务禁止 USB 头、具体类型与协议常量 | 防止源码依赖重新渗透 |
| 业务测试独立链接 | 防止依靠 dust_usb 传递依赖掩盖缺少的真实依赖 |
| 有实际记录行为的测试端口 | 验证命令组、来源身份、提交序号、帧载荷和错误传播，而非只返回 true |
| 现有来源超时、UART 顺序和队列测试 | 保护发送语义，避免接口改动变成行为重写 |
| 多板身份与启动失败测试 | 保护同 bus/ID 跨板路由、整机输出许可和资源回收 |
| 47 项固定报文/签名 | 确认 USB v4 字节格式不变 |
| 控制 fixture 同输入对照 | 确认纯控制输出不因整改改变 |

复用现有测试，只有新的接口绑定和所有权风险需要补充用例，不为每个转调方法机械新增测试。

## 实施顺序与交付边界

1. 先执行措施 1、2、8 中的发送侧部分：公共端口、业务迁移和独立链接。该步完成后即能显著减少业务 USB 依赖。
2. 再执行措施 3、4、5、7：按板移交设备所有权，同时迁移绑定配置与资源回收；这些变更必须一起完成，不能留下悬空借用的中间状态。
3. 再执行措施 6：明确期限归属，数值及行为维持原状。
4. 最后完成措施 8、9 的整体约束与回归，更新接口和架构文档。

每一步保持可编译；不保留旧包装和新接口并存的长期兼容路径。公共声明集中在必要的接口头，现有源文件继续承担原有实现，不为了每个类型增加一对文件。

完成后，USB 仍是当前生产后端；业务可以使用同一组接口接入另一个实现。此计划不实现 EtherCAT 主站、PDO、同步、工作计数器或从站固件。若未来 EtherCAT 从站仍桥接 CAN/UART，可以复用这些端口与设备；若直接控制原生 EtherCAT 电机，需要在 MotorTargets / MotorFeedback 边界接入，不能把原生 PDO 强制伪装成 CAN。
