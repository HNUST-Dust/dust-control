# IgH EtherCAT 通信协议讨论稿

状态：待讨论，未冻结；无对应从站固件、ESI 或运行时实现。
日期：2026-10-26。

## 已确认的范围

- USB 与 EtherCAT 分支分别维护，不要求在同一运行时切换后端。
- `main` 合入当前 `feature/generic-usb-adapter` 重构成果；
  `dev/wbr_infantry_ethercat` 同步 main 后推进 IgH 方案。
- 从站协议尚未实现，先讨论协议，再替换运行时。
- 已确认使用 HPM5E31，预计 1～3 块从站；从站继续作为 CAN/UART 网关。
- 主机保留现有控制、电机编解码和传感器解析，仅替换通信后端。
- 首版接口能力、逻辑通道与设备配置以 USB 版本为基线；使用 YAML 快速配置。
  实际引脚、可用外设、波特率及 EtherCAT 固件能力仍需核对，不能将逻辑编号当作硬件承诺。
- 历史 EtherCAT 代码只覆盖 benchmark 与 MPC 力指令，不满足当前完整控制链路。
  不复用旧 ABI 版本或对象索引来表示不同含义的新协议。

## 当前主机对通信的需求

当前控制器在主机按 1 kHz 执行；电机使用经典 CAN，遥控、HI91 和裁判系统
使用 UART。现有设备解析与控制算法可以保留。

| 数据 | 当前配置 | 需要保留的语义 |
|---|---|---|
| 电机指令 | CAN2/CAN3，各 1 台 DJI 轮电机与 2 台 DM 关节电机 | 同周期完整批次、来源序号、目标生成时间、失效保护 |
| 电机反馈 | 6 台电机，各有明确 adapter / bus / ID | 每台设备独立新鲜度，当前期限 3 ms |
| HI91 | UART2 | 分片与断流处理、采样时间；当前期限 3 ms |
| 遥控 | UART1 | SBUS 丢帧策略、失能后重新使能条件；当前配置期限 1 s |
| 裁判接收 / UI 发送 | UART3 | 字节流顺序、分片、丢块可见、发送拥塞不阻塞控制 |
| 会话保护 | 当前 USB 固件与主机均有保护 | 通信存活不能代表控制目标仍然有效 |

现有逻辑通道号不是新硬件的物理接口数量；新映射需随硬件确定。
现有 20 ms 会话租约也不直接决定新方案的 EtherCAT 看门狗参数。

## 已确定的从站职责

从站负责 CAN/UART 转发、采集时间、缓冲、诊断和本地失效保护；
主机继续承担控制算法、设备协议解析和设备参数管理。
不下沉底盘控制，不引入 USB/EtherCAT 同时切换的通用运行时。

以下字段、布局、容量和状态机均为草案，尚未冻结。

## 建议的过程数据组织

采用固定长度周期 PDO，将控制数据与低优先级字节流分开；不直接把 USB
Hello/Arm/报文队列塞进 PDO。PDO 反复出现的同一个值不能视为新命令或新 UART 数据。

- 主到从控制区：协议版本、会话标识、递增控制序号、使能请求、有效期、固定容量 CAN 指令槽。
- 从到主反馈区：协议版本、启动标识、反馈快照序号、状态/故障、CAN 反馈槽。
  每槽应有独立更新序号和采样年龄/时间戳，未收到新 CAN 帧时不能刷新设备新鲜度。
- 双向 UART 区：通道、块序号、长度、固定容量字节、接收确认及溢出计数。
  明确重复块去重、队满背压、分片顺序、重启丢弃和超时丢弃规则。
- 慢速配置：优先讨论启动期 CoE SDO 配置与读取能力信息；是否支持取决于从站协议栈。
  配置完成并确认前不接受输出使能；OP 状态不自动等于业务使能。

容量需先根据每路 CAN 的波特率、负载、反馈频率及 UART 波特率计算。
反馈若采用“每 ID 最新值槽”，会合并中间样本；必须确认电机解析是否依赖连续帧
（例如角度展开），再决定改用有界事件批次或保留多样本。

## 时间与周期

- 以当前 1 ms 控制周期作为讨论基线；明确接收、计算、发送各阶段以及可接受的一周期延迟。
- 主站 EtherCAT 调用由唯一周期线程持有；业务线程通过有界快照/队列交付数据。
  多板尽量归同一 master/domain 周期统一交换，不让多个线程竞争同一 IgH master。
- 单调时钟用于主机期限判断。若启用 DC，另定义 EtherCAT 纪元时间的来源与换算，
  不直接把主机单调时间当作 DC 绝对时间。
- 首版是否启用 DC 由 ESC/从站支持能力和同步需求决定。
- 未同步时钟时，可用从站采样至发报的年龄换算主机样本时间；还需计入传输/排队延迟，
  指定无效值、回绕处理和允许的最大年龄。

## 必须明确的失效行为

1. 新会话、从站重启、主机重启都进入输出失能态；旧会话指令不能被重放。
2. 连续交换相同控制序号不续控制期限；UART 流量、心跳与 DC 同步不续控制期限。
3. 主站检查链路、从站 OP 和 domain 的 `EC_WC_COMPLETE`，不硬编码 WKC 为固定数字。
   启动等待与运行中故障采用不同规则；故障恢复后不得自动恢复输出。
4. 从站独立实现控制指令期限与 SM 看门狗。即使主机卡死，仍能保护电机。
   不能只依赖主机发送 Stop。
5. 每类电机的安全动作需按协议确定；停止发送 CAN 不一定能停止电机。
   DJI 零电流、DM 失能/保护动作及重复频率需与固件共同验收。
6. 关节、轮电机、遥控或 IMU 失效如何影响整板/整机输出，应保留现有门控语义，
   并明确多板故障传播策略。
7. CAN bus-off、UART 丢块、队满、解析错误和从站复位须有可观察状态，不能静默丢失。

## 冻结协议前需要回答

- HPM5E31 的 ESC/协议栈方案、实际 CAN/UART 接口能力、波特率和设备反馈速率？
- 是否需要 CAN FD、扩展帧或非当前电机的通用 CAN 转发？
- UART 要覆盖哪几路、是否双向、最大带宽和可接受延迟？
- PDO 数据槽采用静态设备映射，还是通道/ID 自描述的固定容量批次？
- CoE/SDO 和 DC 是否可用；设备身份、固件版本、ABI 兼容检查如何完成？
- 指令失效、总线失效、急停及恢复操作的具体时限与安全动作？

确认后交付：带偏移和类型的 PDO 表、对象字典/ESI、主从状态机、时间及序号规则、
带宽预算、错误码、跨语言编解码向量、故障注入测试和硬件验收步骤，再实现主机 IgH 路径。

IgH API 依据：[EtherCAT Application Interface](https://docs.etherlab.org/ethercat/1.6/doxygen/group__ApplicationInterface.html)。

## YAML 配置边界（已确认原则，键名待定）

- `motors_params.yaml` 保留 adapter、bus、协议、CAN ID、方向和期限。
- `sensors_params.yaml` 保留当前传感器参数。
- `dust_control.yaml` 保留具名 Adapter、模块绑定和线程设置；用 EtherCAT
  master、alias/position 与身份校验参数替换 USB serial/VID/PID。
- master 周期和周期线程放在全局 EtherCAT 配置中，不给每块板创建独立 IgH 调用线程。
- 保留 `uart_sensors` 映射；如需可配置波特率，新增显式通道配置，不能假称现有 YAML 已支持。
- 板数、地址、设备绑定、能力和容量在启动前整体校验；能力不满足则报错退出。
  不静默禁用设备、不截断配置、不自动开放输出。
- 字段格式和资源上限固定，通道启用与实际容量由 YAML 决定；启动时生成映射，
  超出主从支持范围则拒绝。容量修改要重新协商和校验，不能单方面改变主机偏移。

## 首版 PDO 字段分组草案

RxPDO/TxPDO 均以从站视角命名；字段采用显式小端编码，禁止直接复制 C++ 结构体。
下表只定义职责，暂不分配对象索引、字节偏移和容量。

| 方向 / 分区 | 候选字段 | 语义 |
|---|---|---|
| RxPDO 控制 | ABI 版本、会话标识、控制序号、控制标志、剩余有效期 | 新目标才推进控制序号；到主站发送时须扣除目标已消耗的寿命 |
| RxPDO CAN | 批次计数、来源、通道、ID、长度、标志、8 字节载荷 | 当前经典 CAN 能力；完整批次校验通过后才接纳 |
| RxPDO UART | 通道、块序号、长度、字节、上行块确认 | 与控制序号独立，不能替控制续期 |
| TxPDO 公共状态 | ABI、从站启动标识、会话回显、状态、故障、配置签名 | 检测复位、错配及保护状态 |
| TxPDO CAN | 批次序号、帧数、每帧通道/ID/长度/标志、总线序号、采样时间、载荷 | 有界原始帧事件；明确确认、保留和溢出策略后确定容量 |
| TxPDO UART | 通道、块序号、长度、采样时间、字节、下行块确认 | 重复块去重，丢块触发现有 Discontinuity 逻辑 |
| TxPDO 诊断 | CAN/UART 溢出计数、总线故障、指令拒绝及保护原因 | 高频关键状态进 PDO，详细计数可放慢速读取 |
| TxPDO 板载 IMU（已确认保留） | 原始采样、采样序号、时间和温度 | 保留 USB 原始 IMU 能力，具体 HPM5E31 接线另行映射 |

USB 每请求最多 6 帧 CAN、UART 下行最多 96 字节、上行块 40 字节，
这些是消息容量，不是每毫秒吞吐保证。EtherCAT 容量需结合多个 USB 报文的实际流量计算，
不能直接采用“每周期 6 帧/40 字节”来宣称能力等价。

## 启动与保护状态机草案

1. 加载并校验全部 YAML；禁止输出。
2. 申请 IgH master，核对配置从站身份与能力，建立 PDO 映射。
3. 在协议栈支持的状态下下发启动配置（优先讨论 CoE SDO），从站原子应用并返回配置签名。
   若必须先进入 OP，业务仍保持失能；AL 状态与业务状态分离。
4. 周期交换建立后确认 OP、完整 WKC、ABI、启动标识、配置签名和新会话。
   只有这些检查通过才进入业务就绪态；握手不等于电机输出使能。
5. 保留当前主机输出配置、遥控失能确认、设备新鲜度及恢复门控，满足后发送有效控制。
6. 任一必要板故障时先取消整机输出许可，健康板发安全指令；故障板依靠本地保护。
   是否统一终止全部会话及允许恢复的流程，仍需冻结。
7. 停止/超时/从站复位进入保护；不会因为 OP 恢复、PDO 重复或 UART 活动自动使能。
   重建会话后仍需重新经过完整门控。

仍需单独设计：控制与 UART 去重/确认的回绕规则、CAN 新鲜度与积压上限、
多控制来源独立期限、DM 一次性指令语义、SDO 配置对象、SM 看门狗时限及硬件安全动作。
这些确定后再产出带偏移的可实现线协议。

## 容量预算方法与当前证据

当前配置有 6 台电机，DJI 指令按总线及命令 ID 合并，DM 指令按电机生成；
现有 CAN 发送器每来源最多注册 16 个命令组，USB 单包最多容纳 6 帧。
这些限制属于不同层，EtherCAT 不能只复用最小的一个限制。
当前仓库没有足以证明所有通道持续满载的实测数据。生产 UART 线路参数现已从用户提供的
USB 固件及其板级设备树核对，见下文；线路上限仍不等于实际传感器流量。

设周期为 T 秒，每条总线/串口按实际启用配置求和：

- CAN 下行容量至少覆盖同周期所有来源的完整命令组，并预留一次性设备指令的处理方式。
- CAN 上行平均需求为 `T × 各设备反馈帧率之和`；最终容量还要覆盖突发，
  确认往返期间保留的数据，以及约定可容忍的主机调度抖动。
- UART 每周期需求为 `T × 波特率 / 每字符线路位数`；8N1 是 10 位，
  SBUS 等格式须按实际起始位、数据位、校验位及停止位计算。
- 例：单路 115200/8N1 持续流量为 11.52 字节/ms；单路 921600/8N1 为
  92.16 字节/ms。两者只是计算示例，不是已确认的产品配置。
- 停等确认时，有效吞吐为 `每块字节数 / 实际确认往返时间`；不能直接按每周期一块估算。
  如需滑动窗口，必须同时确定窗口大小、缓冲和确认格式。
- 三板链路预算按实际 PDO 总字节数计算，并计入 EtherCAT/Ethernet 分帧、
  datagram、线缆传播、ESC 转发、主机处理及周期余量；不能只检查理论线速。

冻结容量前需补齐：生产固件通道表及波特率、最大反馈频率、UART 峰值流量、
允许的突发/停顿时间，以及 HPM5E31 固件的过程数据与缓冲资源限制。

## 序号、确认和超时建议

以下为待评审规则，尚未成为主从实现契约。

### 所有流共用的规则

- 使用会话标识和从站启动标识隔离重启前后的数据；新会话清空旧待发与去重状态。
- 32 位流序号按模 2^32 比较：差值为 0 表示重复；差值在 1..2^31-1 表示向前；
  其他情况拒绝。会话内不得存在跨越半个序号空间的未确认跨度。
  初始序号由显式“尚无数据”状态区分，不能把 0 永久保留为无效值后又允许自然回绕。
- 同序号必须保持相同内容；改变载荷必须分配新序号。
- 确认仅表示数据已由接收端校验并接纳，不表示 CAN 电机或 UART 外设已执行。

### 控制下行：最新批次与一次性动作分别处理

- 主机仅对新生成的控制批次推进来源序号；周期线程反复复制相同批次不推进该序号。
- 各来源保持独立生成时间与期限；主站发送时扣除主机内等待时间，
  从站按首次接纳时刻和剩余寿命计时，重复批次不能重置期限。
- 空批次可以保留原有“控制来源仍在运行”的语义，但不意味着从站可以重放上次 CAN 指令。
- 一个来源失效不得由另一个来源、UART 或总线交换续期；故障是否停整板按最终状态机执行。
- 连续控制不积压重传旧批次，新的完整目标可替代尚未派发的旧目标。
  DM 使能/失能等动作须有单独事务身份或明确的安全幂等重试约定，不能被目标覆盖悄悄吞掉。
- “批次原子接纳”只表示校验和入队的一致性，不承诺多个 CAN 控制器同时发送、
  也不承诺总线硬件发送成功的全有或全无；部分发送失败必须进入故障处理。

### CAN 上行：不做可靠重传（已确认）

- 保留原始帧批次、每总线序号和采样时间；主机只交付新发布的批次。
  同一 PDO 影像可能重复出现在多个交换周期，但不能重复交给解析器。
- 不设置 CAN 反馈接收确认，不因主机未接收而保留并重发历史批次；
  有新数据时推进批次序号并发布新批次，无新数据时不刷新采样时间。
- 原 USB 使用有界 FIFO，并不保证队满时自动保留最新帧。
  EtherCAT 按用户要求优先新鲜度：容量不足时丢弃较旧的待发布事件，
  保留最新的有界事件窗口；具体并发缓冲实现待实现阶段验证。
- 保留窗口内的接收顺序，不直接改为“每 ID 一个最新值槽”；
  这避免无条件合并所有中间帧，但仍可能丢样，不能保证角度展开连续性。
- 批次号、总线序号与累计丢弃计数暴露交换丢失和从站积压丢弃；
  主机不得将缺失帧补成新反馈，须核查解析器对缺帧的处理与恢复。
- 最新仅表示优先发布最新可用数据，不代表每周期设备都产生新数据，
  也不构成端到端实时性保证。每设备新鲜度仍按真实采样时间判断。
- 每总线保留独立容量或配额，避免繁忙总线挤占其他总线的有效反馈；
  容量、截断与超龄丢弃阈值待布局冻结时确定。

### UART 双向：各路独立的有界顺序流（分配原则已确认）

- 六路各有固定数据容量、长度、序号、采样信息和丢块状态；
  UART2 分配高于其他端口的容量。各路独立缓冲，不借用 CAN 或其他 UART 的保底容量。
- UART 接收是字节流，不能照搬 CAN 的“旧块被最新块覆盖后无感继续拼接”；
  发生丢块须显式断流并调用现有 Discontinuity。
- 具体字节数、确认及流控方案仍待定；按实际确认往返计算吞吐，
  避免把每毫秒的线路需求误当停等协议可持续达到的带宽。
- 若采用确认/重传，重复块不能重复交付；UART 下行确认前须预留完整块容量。
  确认仅表示接纳，复位期间外设执行结果可能未知，不承诺跨重启恰好执行一次。
- 采样时刻固定；若年龄字段随 PDO 发布，重发时年龄须继续增长，不能刷新为新采样。
- 队满、过期和缺口均须可见；剩余消息的丢弃/恢复规则不得把旧消息尾部拼接到新消息头部。

### 时限分离

分别定义控制来源期限、从站指令有效期、SM 看门狗、设备采样新鲜度、
流确认超时和启动等待超时；数值可有关系，但不能用同一个“20 ms”覆盖所有含义。
保留当前 3 ms 电机/HI91 新鲜度要求后，必须核算周期延迟、确认等待与突发积压的总年龄；
增加队列深度不代表可以放宽该要求。

### 缓冲与交付语义

- `src/drivers/can_port.cpp`：每总线软件 TX FIFO 深度 32，完整批次接纳前检查空间；
  发送白名单和精确接收过滤器来自生成配置。CAN0/1 虽配置了波特率，但设备列表为空，
  不表示可任意透传所有 ID。
- `src/usb_reports.cpp`：CAN 上报队列共享 128 帧，传感器报告共享 128 包，回复队列 16 包；
  上行线程优先回复，再交替服务 CAN 与外设，不固定每毫秒只发送一个 USB 包。
- `src/drivers/uart_port.cpp`：每 UART 两个 128 字节 RX DMA 缓冲，空闲超时 1000 us，
  上报切成最多 40 字节块；每路 TX 队列 8 块，每块最多 96 字节。
- `src/drivers/usb_transport.cpp`：USB OUT 软件队列深度 16。
- 队列深度是抗突发能力，不能直接换算成可容忍的控制/传感器延迟。

### 安全配置与 YAML 的真实边界

`config/can_devices.yaml` 是固件编译期输入：四路 CAN 各 1 Mbps，
CAN2/3 各绑定一台 DJI 和两台 DM，`command_timeout_us: 20000`、`protect_on_boot: true`。
DJI 保护载荷为八字节零，DM 为 `ff ff ff ff ff ff ff fd`。
`firmware_can_profile.hpp` 不允许会话删除或替换 MCU 的 CAN 保护表，
主机仅能选择不超过固件上限的租约及补充 UART 停止动作。

`gateway_runtime.cpp` 在启动及关闭会话时向 CAN 队列提交保护帧；关闭时替换软件业务队列，
但已进入硬件的帧无法撤回。源码未体现持续周期重发整张保护表，不能称为已保证送达。
CAN/UART 输出故障、USB 连接变化和相关传输故障可关闭已授权会话；
主循环的 USB 接收等待为 1 ms，但这不是经过测量的保护响应时间上界。

因此，“与 USB 保持一致”默认保留主机设备绑定与固件保护配置的职责边界。
若希望改主机 YAML 后无需重编固件就变更 CAN 白名单、波特率和保护帧，
这属于新增启动配置能力：需要定义可写范围、原子提交、签名回读与本地保护兜底，
不能当作单纯替换后端时自然已有的功能。

### 对 PDO 方案的直接影响

- UART 容量应按六路聚合线路预算与实际负载共同评估，并提供每端口公平性；
  一块板所有 UART 共享单个小块会形成瓶颈。
- CAN 上行不能仅按当前六台电机计数；必须明确是覆盖配置白名单反馈负载，
  还是承诺四路 CAN 更广泛的接入能力。首版仍按白名单网关设计。
- 不采用把 USB 128/160 字节包原封不动映射为唯一周期 PDO 的方案。
- 保留受固件约束的安全参数；任何新增动态配置在从站失能状态应用并确认。
- 当前已有线路上限和队列证据，仍缺设备实际反馈频率、突发统计、
  HPM5E31 过程数据资源及实机周期余量；PDO 槽数继续标为未冻结。

## 首版周期基线（2026-10-26 已确认）

- 首版 EtherCAT 通信周期固定为 **1000 us（1 kHz）**，底盘控制周期保持 **1000 us**。
- 本阶段不启用 500/250 us 通信周期，不因 EtherCAT 存在更短周期的产品案例改变基线。
- 周期、主站索引、周期线程与板卡绑定的设计示例见
  [ethercat_pdo.yaml](../config/ethercat_pdo.yaml)。这已接入离线布局工具，
  不能替换当前 `config/dust_control.yaml`；后者仍是 USB 装配配置。
- 后续配置加载器须校验通信周期；首版拒绝不支持的周期值，不能接受 YAML 后静默忽略。
  底盘周期仍以当前控制器常量为准，示例不表示其已经支持运行时改频。
- 1～3 块板共享一个 IgH 周期线程；不按板分别 sleep，不随板数扩大名义周期。
- 周期唤醒使用单调时钟的绝对时间；记录错过的周期，错过后跳过已过期释放点，
  不在恢复调度后连续突发补发历史目标。
- 主站 API 由周期线程统一调用；周期内接收并处理反馈、发布观测、
  读取当前有效目标、写 PDO、排队并发送。底盘仍通过有界数据交接运行，
  不假定两个同频线程天然有固定先后顺序。
- 反馈到目标的相位关系及最大一周期等待纳入端到端延迟预算；
  既有 3 ms 设备新鲜度要求保持不变，不能因排队或重传自动放宽。

### 实现与验收要求

当前完成的是设计基线与配置示例，IgH 运行时及配套从站尚未实现。
接入代码时应同时完成：

1. 周期配置加载/校验和单位换算，未知字段、非法周期、重复从站绑定启动前拒绝。
2. 周期线程绝对定时、唯一 master 所有权、过期目标拒绝和异常退出回收。
3. 统计周期唤醒抖动、最长执行时间、错过周期、WKC 异常、从站非 OP、
   每设备数据年龄和队列溢出；分开统计 EtherCAT 交换周期与设备真实更新周期。
4. 对 1 板和 3 板配置，在无输出条件下验证正常负载与通信峰值，并记录测试时长和环境；
   接受阈值在硬件测量后明确，不能只凭平均频率达到 1 kHz 判定通过。
5. 注入主机停顿、断线、从站重启和旧序号重复；验证从站独立保护且恢复不自动使能。

后续只有在 1 ms 基线验收后，才评估 500/250 us。届时保持底盘 1 kHz，
单独测量通信提频对转发等待的收益及 CPU/链路成本，再决定是否开放 YAML 选项。

## 本轮确认的协议决策

- **保留全部 USB 能力**：CAN/UART 双向、板载原始 IMU、能力与状态查询、
  诊断及安全保护均纳入首版兼容范围；USB 特有枚举、端点和会话传输错误改用 EtherCAT 对应机制，
  不要求复制 USB 传输格式。板载 IMU 温控等本地功能继续归固件，不因替换通信而丢失。
- **UART 独立分配**：六路分别配置固定容量、序号和缓冲，UART2 优先增加容量；
  用户确认的是分配原则，具体字节数仍需预算和从站资源验证。
- **CAN 不做可靠重传、优先最新**：使用带序号和时间的最新原始事件窗口；
  不等确认、不追发旧反馈。原 USB 的有界 FIFO 不等于无条件保留最新，
  因而需明确 EtherCAT 的超龄/溢出丢旧策略，并保留丢帧可观察性。

下一步布局需要填写：每总线 CAN 窗口帧数、六路 UART 双向字节数、
板载 IMU 区、公共状态区，以及 UART 交付/流控方式。以上数值尚未获确认，
不会将此前举例的每板 512 B 下行/1024 B 上行当作既定容量。

具体容量、偏移和字段候选见 [PDO 布局提案 v0](ETHERCAT_PDO_LAYOUT_V0.md)；仍未冻结，UART 窗口机制尤其需要评审。
